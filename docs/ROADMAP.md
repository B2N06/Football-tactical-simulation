# 优化路线与实现可行性

以下“实现可能性”是基于当前 Electron、TypeScript、SQLite 和蒙特卡洛架构的工程估算，不代表数据提供商一定开放相应数据。

### v0.5.0 同类项目调研结论

- `tacticalboard/tacticalboard` 验证了轻量、设备内可用的战术板交互价值；本项目保留单窗口、低学习成本的方向。
- `gljubojevic/tactics-board` 的可编辑战术文档与关键帧思路有参考价值。本轮先落地编辑历史和显式保存；关键帧仍列入后续。
- `PySport/kloppy` 的提供商无关数据模型、坐标方向转换和事件筛选值得持续借鉴；本项目已坚持统一 105 × 68 米坐标与标准交换结构，后续优先补事件片段筛选。
- `openfootmanager/openfootmanager` 展示了桌面端本地存储与后台模拟的组合价值；本项目继续保持 SQLite 与 Worker 离线计算，不引入其 GPL 代码。

以上只借鉴公开功能思路；本仓库未复制这些项目的源代码或视觉资产。

## 推荐顺序

1. 先完成球队分析的时间/赛事/主客场筛选、事件下钻，以及“从 360 快照创建情景”，打通分析、复盘和推演闭环。
2. 再补充分钟数、xT/OBV 类价值指标、时间衰减和跨提供商身份匹配，提高球员与球队评估精度。
3. 随后增加连续攻防球权状态机、暂停和多 Worker，使实验更接近真实战术阶段并支持更大批量。
4. 定位球、图形导出、参数回测、自动更新、代码签名和 AI 扩展保持为独立模块。

## 模型边界

- 事件数据可以可靠校准有球倾向，但不能独立证明无球跑位和防守站位。
- 热点图图片只作为参考叠加，不应从像素反推训练坐标。
- 商业数据源能否提供球员坐标、速度或压力数据取决于订阅许可，适配器实现成功不等于数据覆盖可用。
- 所有输出继续标记为概率分析，不将结果描述为真实比赛预测。
