# 架构说明

## 桌面边界

Electron 主进程负责文件选择、SQLite 持久化、数据源网络请求、安全存储和报告导出。React 渲染器启用上下文隔离、禁用 Node.js，仅能通过 `preload` 暴露的白名单 IPC 调用主进程。

## 数据流

1. 数据提供商或本地文件进入适配器。
2. 适配器转换为 `CanonicalMatchBundle` 并统一坐标。
3. 预览展示覆盖率、警告和错误；确认后使用 SQLite 事务写入。
4. 用户可从已导入比赛创建历史校准方案；数据库会自动查找同一提供商中包含相关球员的最多 20 场比赛，事件样本用于平滑行为倾向，有球员 ID 的追踪帧用于校准站位与置信度。
5. 球员历史先验与人工战术参数组成 `TacticalScenario`，低样本球员使用位置先验补足并明确标记；主客队归属通过阵容成员关系判断，不依赖提供商球员 ID 格式。
6. Web Worker 分别运行基准与修改方案，以流式聚合方式返回可复现的 `SimulationComparison`，不会长期保存全部回合对象。

## 浏览器边界

`src/platform/browserApi.ts` 实现与 Electron preload 相同的 `DesktopApi` 合同。没有桌面桥接时注册此实现；存在 Electron 桥接时不覆盖它。比赛库和方案使用 IndexedDB 原子事务，导入先完整验证再写入，备份为标准 JSON。浏览器持久化按站点与设备隔离，不是云端数据库。

公开 StatsBomb 下载在浏览器直接访问固定 GitHub 地址；每个请求有 30 秒超时和 75 MB 上限。football-data.org 由 `public/_worker.js` 的固定同源代理处理，禁止任意目标 URL，只接受 GET、指定赛事测试路径和数字比赛 ID，校验 Origin、Token、请求频率并限制 25 秒/8 MB。Token 只在页面内存中使用，不持久化。

`vite.web.config.ts` 单独构建网页，产物包含 Pages Worker、路由和安全响应头。React、球员编辑、规则分析与蒙特卡洛引擎在两种平台间共用；网页 PDF 使用打印窗口保存，桌面版使用原生导出。

比赛分析必须读取当前选择的 bundle，而不是当前编辑方案。只有置信度为 `observed` 且 ID 能匹配阵容的坐标可标记为球员观测；无身份的 360 点位不能冒充具名球员追踪。缺失 xG 不当作零值，已知 xG=0 仍计入覆盖。

## 球队分析数据流

1. 用户选择一场基准比赛和其中一支球队。
2. 主进程按“相同提供商 + 稳定球队 ID”读取最多 30 场比赛，并始终把基准比赛置于首位。
3. 渲染进程中的确定性分析引擎汇总球队与这些比赛中实际对手的指标，不访问网络、不调用 AI。
4. SQLite 的 `match_teams` 索引按提供商和稳定球队 ID 直接定位候选比赛；旧数据库启动时自动回填，避免数据量增长后扫描并解析全部比赛 JSON。
5. 页面展示逐场趋势、阶段和区域分布、阵型使用、球员贡献、传球连接、证据型复盘重点与数据覆盖说明。

球队分析使用的 `CanonicalMatchBundle` 事件坐标已经按“每个行动球队从左向右进攻”标准化，因此不能再按主客场或上下半场二次翻转。场地倾斜是双方进攻三区事件的相对占比；事件占比不是控球率；PPDA 仅为事件口径近似值；球员参与指数是当前样本内的启发式相对指标，不等同于球员能力或比赛评分。

## 推演边界

引擎是带连续位置状态的事件序列蒙特卡洛模型，不是逐帧物理引擎。每个动作步都会更新双方 22 人的位置；防守方根据皮球位置、盯人、压迫、防线高度、速度和耐力响应。传球、带球、射门和防守压力的概率由球员属性、职责、距离、空间与球队设置共同决定。没有逐帧坐标时生成的无球跑位必须标记为模型推断。

推演场景使用同一张共享球场：主队持球时向右进攻，客队持球时向左进攻；推进、射门目标、禁区进入和左右通道均按球权方视角计算。这个规则只用于 `TacticalScenario` 的共享空间，不得套用到已经标准化的历史事件坐标。

`AiAnalysisProvider` 只是未来扩展边界；首版只有会拒绝调用的 `DisabledAiProvider`。
